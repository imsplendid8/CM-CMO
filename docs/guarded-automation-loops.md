# 가드레일 기반 자동화 루프

문서 상태: **제안**. 이 문서는 구현 완료 목록이 아니라 다음 자동화의 도입 순서와 사람 승인 경계를 정한다.

[oss-leverage.md](oss-leverage.md)가 현재 활용 중인 OSS와 후보를 정리한다면, 이 문서는 해당 도구를 어떤 운영 문제에 적용하고 어디에서 자동화를 멈출지 설명한다.

## 도입 판단

| 후보 | 결정 | 적용 범위 | 도입 조건 |
|---|---|---|---|
| [Playwright](https://github.com/microsoft/playwright) | 기존 사용 확장 | 핵심 5화면 데스크톱·390px 시각 회귀 | 고정 fixture와 사람 승인 baseline |
| [Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) | 작게 도입 | CM-CMO Pages 핵심 화면의 접근성·SEO·성능 하한 | 낮은 하한으로 시작해 오탐과 시간을 관찰 |
| [Dependency Review](https://github.com/actions/dependency-review-action) | 의존성 추가 시 도입 | 패키지 변경 PR의 취약점·라이선스 검토 | 실제 manifest·lockfile 변경이 있는 PR만 실행 |
| [Renovate](https://github.com/renovatebot/renovate) | 보류 | 고정 의존성 갱신 PR | npm/Python 고정 의존성이 늘어난 뒤 월 1회 |
| [Super-Linter](https://github.com/github/super-linter) | 현재 제외 | — | 기존 맞춤 검사가 부족해질 때 재평가 |
| [OpenTelemetry JS](https://github.com/open-telemetry/opentelemetry-js) | 현재 제외 | — | 인증된 Worker API와 D1 처리가 커질 때 재평가 |

Playwright는 새 도입이 아니다. 현재 SERP 캡처 사용 범위를 제품 UI 회귀로 확장한다. Lighthouse CI는 외부 담당 사이트를 월간 점검하는 기존 Unlighthouse와 달리, CM-CMO Pages 자체의 PR 회귀를 확인하는 보완 수단으로만 쓴다.

Renovate를 도입할 때는 관련 패키지를 그룹화하고 major 버전 자동 병합을 금지한다. 테스트 통과만으로 자동 병합하지 않으며 Playwright 패키지와 브라우저 버전을 함께 관리한다.

## 공통 운영 계약

모든 자동화는 다음 다섯 값을 남겨야 한다.

- 마지막 성공 시각
- 입력 데이터 기준일
- 생성 후보 수
- 사람 승인 상태
- 실패 이유

이 값을 남기지 못하면 실행 성공만으로 운영 루프를 완료 처리하지 않는다. 후보 생성과 상태 계산까지만 자동화하고, 최종 채택은 사람 승인으로 남긴다.

## 1순위: 월간 수요 발견

```text
SearchAd 월 스냅샷
→ 전월 대비 급상승 후보 계산
→ 데이터랩 추세 교차 확인
→ 담당자 리뷰
→ 채택·보류·제외 사유 기록
→ 다음 달 오탐률 평가
```

초기 후보 기준은 다음과 같다.

- 신규 키워드: 전월 0회, 당월 100회 이상
- 급상승: 전월 10회 이상
- 전월 대비 50% 이상 증가
- 동시에 최소 50회 이상 증가

월별로 후보 수, 검토 수, 채택·보류 수, 오탐 사유, 다음 달 유지 여부를 기록한다. 자동 입찰, 캠페인 생성, 예산 변경은 하지 않는다.

## 2순위: 데이터 장애 복구

```text
Actions 완료
→ 6개 데이터 산출물 검사
→ 실패 시 1회 재시도
→ 계속 실패하면 중복 없는 Issue 또는 담당자 알림
→ 복구되면 같은 incident를 종료
```

- 자동 재시도는 1회까지만 허용한다.
- 데이터 소스와 오류 fingerprint로 동일 알림을 중복 생성하지 않는다.
- 실패를 정상으로 바꾸거나 마지막 성공 시각을 덮어쓰지 않는다.
- Secret과 전체 요청 헤더를 로그에 남기지 않는다.
- Issue 자동 종료는 동일 incident가 실제로 복구된 경우에만 허용한다.

첫 구현은 6개 데이터 산출물의 상태 파일과 수동 dispatch로 제한한다. 자동 Issue 생성·종료는 별도 PR에서 권한과 중복 제거를 검증한 뒤 연결한다.

## 3순위: 다음 달 소재 준비

매월 20일 한 번 다음 달 연간플랜에서 시즌·뉴스·검색량 근거를 모아 상품별 소재 후보를 만든다.

- 모든 결과는 `심의 검토 전`, `상품 근거 미확인`, `운영 후보` 상태다.
- 선택 월, 입력 데이터 기준일, 규칙 버전을 함께 기록한다.
- 데이터가 오래됐으면 전월 문구를 자동 재사용하지 않는다.
- 자동 실행은 월 1회이며 담당자가 필요할 때만 수동 재실행한다.
- 실제 광고계정 업로드는 수행하지 않는다.

## 4순위: 추천 품질 개선

인증과 저장소가 생긴 뒤 `채택 / 수정 필요 / 반려`와 사유 코드를 수집한다. 원문 광고문구보다 추천 fingerprint, 상품, 이벤트, 상태, 기준일, 규칙 버전을 우선 저장한다.

피드백이 운영 규칙이나 프롬프트를 즉시 바꾸게 하지 않는다. 월 1회 변경 PR을 만들고 회귀 테스트와 사람 승인을 거친다.

## 5순위: UI 시각 회귀

홈, 연간플랜, 월간 급상승 키워드, 검색광고 소재, SEO 화면을 데스크톱과 390px에서 캡처한다. 차이 이미지는 artifact로 올리되 기준 이미지는 사람이 승인한 경우에만 변경한다.

동적 날짜와 API 데이터는 fixture로 고정하거나 비교에서 마스킹한다. 첫 PR은 겹침, 잘림, 가로 스크롤, 필터 줄바꿈 같은 큰 회귀만 다룬다.

## 6순위: FAQ 품질 유지

상품 1개에서 최대 4개의 FAQ로 시작한다. 화면 문구와 JSON-LD가 같은지 검사하고 상품설명서·약관 근거를 확인한다. 분기마다 유지·수정·삭제를 검토한다.

구조화 데이터에만 답변을 숨기거나 생성형 답변으로 보험료·담보·면책 조건을 확정하지 않는다.

## 자동화 경계

다음 작업은 사람 승인 없이 자동화하지 않는다.

- 보험 광고심의 최종 승인, 담보·면책·감액·보험료 사실 확정
- 자동 입찰, 실제 광고계정 업로드, 예산 변경, 캠페인 on/off
- Telegram 실제 발송과 수신자 변경
- Secret 생성·교체·공개
- 기준 이미지 변경과 추천 규칙의 즉시 반영
